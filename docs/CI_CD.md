# Civilist: проверки и выпуск через GitHub

CI проверяет версию кода. CD доставляет выбранную версию на работающий сайт. GitHub запускает команды на своём временном Linux-компьютере; Mac при этом можно выключить.

## Что есть сейчас

4 октября 2026 года Дмитрий развернул `civilist-qa`, применил миграцию к `civilist-db-qa`, загрузил три QA-секрета и сообщил об успешном входе, прохождении учебного теста и сохранении опыта. Это быстрая ручная проверка. Проверку роли администратора, второго устройства и независимости основного прогресса ещё нужно завершить.

| Часть | Назначение | Что происходит с данными |
|---|---|---|
| `master` | Основная версия исходного кода | Данных пользователей в ветке нет |
| Ветка изменения и PR | Предлагаемая версия кода | Создание ветки не создаёт сайт и не копирует базу |
| Основной сайт `civilist` | Работающее приложение для пользователей | Постоянная `civilist-db` |
| Общий QA `civilist-qa` | Ручная проверка одной выбранной версии | Постоянная отдельная `civilist-db-qa` |
| Локальное окружение CI | Автоматические API-проверки каждого запуска | Свежая временная D1, удаляемая после проверки |

QA начинается с материалов из `content/seed.json`. Это не копия основной базы. При обновлении кода QA-опыт и административные правки сохраняются; миграции могут изменить схему, поэтому их тоже проверяем. Новое развёртывание другой ветки заменяет код общего QA, сохраняя его базу.

## Как это соотносится с GitLab

| В привычном процессе | В Civilist на GitHub |
|---|---|
| Merge request | Pull request |
| Pipeline | Запуск GitHub Actions |
| Job | Задача или шаг workflow |
| Environment и кнопка Open | Окружение `qa` и ссылка на стенд в результате развёртывания |
| Review app для каждого MR | Возможный следующий этап: отдельные Worker и D1 на каждый PR |

Название Environment само по себе не означает копию базы. В прежнем проекте способ подготовки данных задавался скриптами команды. Здесь схема и начальные материалы известны из репозитория; основная база автоматически не клонируется.

## Что делают подготовленные workflows

**Check Civilist** запускается на каждом PR и после изменения `master`. Он проверяет TypeScript, 21 тест авторизации и конфигурации, сборку интерфейса и сборку обоих Workers без публикации. Затем `npm run test:integration` создаёт временные коды, применяет миграции к временной локальной D1, запускает настоящий Worker на свободном локальном порту и выполняет 49 проверок API. Проверяются вход, роли, сохранение профиля и опыта во второй сессии, независимость опыта администратора, повторная отправка ответа, закладки, редакционный доступ и сохранение черновика без публикации.

Тесты не используют коды основного сайта или QA. Временная конфигурация содержит только локальную D1; команды явно используют `--local`. API-тест отказывается работать с адресом за пределами `localhost` и `127.0.0.1`. Локальные секреты и база удаляются после запуска. Тесты браузерного интерфейса на Playwright ещё не добавлены.

**Deploy Civilist** запускается кнопкой `Run workflow`. В нём выбираем ветку и окружение:

- `qa`: доставить выбранную ветку на общий тестовый сайт;
- `production`: выпустить только выбранный `master` на основной сайт.

Перед доставкой повторно проверяется именно commit этого запуска, включая API с временной D1. При ошибке выпуск не начинается. Доставка проверяет выбранные Worker и базу, применяет их миграции и загружает код. Установленные коды входа остаются в Cloudflare. Одновременные развёртывания одного окружения не выполняются.

После загрузки проверяются страница входа и ожидаемый отказ API без сессии. Эта проверка не входит в аккаунт и не проверяет живую D1. Ссылка на сайт и точный commit остаются в результате запуска. Ссылка общего QA всегда показывает последнюю развёрнутую там версию; записанный commit относится к конкретному запуску.

Push, открытие PR и слияние сами по себе не публикуют код. Слияние PR объединяет код и SQL-миграции; данные QA при этом не переносятся в основную базу.

## 1. Завершить включение настроек в master

1. На QA проверь вход администратора и его доступ к редактированию.
2. На основном сайте проверь прежний вход и сохранённый опыт. Учебные действия QA не должны появиться там.
3. При успешной проверке включи PR #2 с конфигурацией QA в `master`.
4. Проверь зелёный `Check Civilist` и включи PR с этой автоматизацией в `master`.

Файл `deploy.yml` должен попасть в основную ветку, чтобы появилась кнопка `Run workflow`. До этого подготовка кода не означает, что CD уже включён. Если файлы workflow отличаются в старой рабочей ветке, сначала обнови её свежим `master`.

## 2. Дать GitHub технический доступ к Cloudflare

Это отдельный API-токен для доставки кода. Он отличается от кодов входа в Civilist, редакционного токена и личного GitHub-токена. Его значение вводится только в Cloudflare и настройки GitHub.

1. В Cloudflare открой **Account API tokens → Create Token** и создай токен с понятным именем, например `Civilist GitHub deploy`.
2. Для текущих Worker и D1 нужны разрешения аккаунта **Workers Scripts → Edit**, **D1 → Edit** и **Account Settings → Read**. Ограничь доступ своим аккаунтом, где находятся `civilist` и `civilist-db`. DNS и доступ к чужим аккаунтам этому проекту не нужны.
3. Сохрани выданный токен в менеджере паролей. Не вставляй его в Git, терминальные команды или чат.

Токен с этими разрешениями даёт доступ к Workers и D1 выбранного аккаунта. GitHub-окружение `qa` отделяет выдачу секрета workflow; оно не делает аккаунтный Cloudflare-токен ограниченным одной QA-базой.

## 3. Настроить GitHub-окружение qa

Открой [репозиторий](https://github.com/Pandasayok/civilist) → **Settings → Environments → New environment**, имя `qa`.

| Раздел в окружении | Имя | Значение |
|---|---|---|
| Environment secrets → Add secret | `CLOUDFLARE_API_TOKEN` | Созданный Cloudflare API-токен |
| Environment variables → Add variable | `CLOUDFLARE_ACCOUNT_ID` | ID аккаунта Cloudflare, где находятся обе базы |

Account ID — не Database ID. ID аккаунта виден в панели Cloudflare; тот же ID был показан командой `wrangler whoami`. Коды ученицы и администратора, `.civilist-secrets-qa.json` и ключ сессии в GitHub не нужны: они уже установлены в QA Worker.

Сначала подключи только `qa`. Для выпуска через GitHub позже создай окружение `production` с такими же именами секрета и переменной. В **Deployment branches and tags** окружения `production` выбери **Selected branches and tags** и разреши ветку `master`. Workflow дополнительно проверяет этот выбор. Пока `production` не настроено, основной сайт можно выпускать прежней командой `npm run deploy` из проверенного `master`.

## 4. Первый запуск QA через GitHub

1. Открой **Actions → Deploy Civilist → Run workflow**.
2. В **Branch** выбери `master` для первого пробного запуска; окружение оставь `qa`.
3. Нажми **Run workflow** и открой появившийся запуск.
4. Дождись успешных `select`, `validate` и `deploy`.
5. Открой QA по ссылке окружения или **Открыть стенд** в отчёте. Войди своим уже созданным QA-кодом и проверь сохранённый тестовый прогресс.

Если токен или ID отсутствуют, workflow завершится понятной ошибкой до миграций. Если развёртывание прошло, а проверка сайта завершилась ошибкой, код уже мог быть загружен: сначала посмотри журнал `deploy`, затем проверь сайт. Автоматического отката миграций нет; возврат старого кода не возвращает старую схему или данные.

## 5. Обычная доработка

1. Разработчик создаёт `feature/...`, `fix/...` или `test/...` от свежего `master`. Код функции и её тесты меняются вместе в этой ветке.
2. Открываем PR. Автопроверки запускаются на предлагаемой версии. Внешним PR не выдаются секреты Cloudflare.
3. После зелёных проверок запускаем **Deploy Civilist**, выбираем ветку PR и `qa`. Доставку запускаем только для проверенного кода из своего репозитория.
4. Дмитрий проверяет функцию на QA, фиксируя commit, шаги и результат в PR. Исправления отправляются в ту же ветку; CI запускается снова, QA нужно обновить новым запуском доставки.
5. После успешной проверки сливаем PR. Проверки снова идут на `master`.
6. Выбираем **Branch: master**, **environment: production**, нажимаем **Run workflow**, затем проверяем основной сайт.

База QA продолжает жить отдельно. Для чистого набора данных автопроверок используем временную D1, а не очистку общей QA-базы.

## Стоимость и следующий этап

Репозиторий сейчас публичный. Стандартные GitHub-hosted Linux runners бесплатны для такого репозитория, а Environments доступны на GitHub Free. Используем `ubuntu-latest`, без больших платных runners и загрузки тестовых баз в артефакты. Cloudflare Workers и D1 остаются на общем Free-тарифе аккаунта с его квотами. Дополнительная подписка на CI/CD не требуется.

Дальше можно добавить Python + Playwright: вход, прохождение задания, обновление страницы с сохранением результата и различия ролей. Это дополнит API-проверки проверкой кнопок и интерфейса. Отдельные сайты для каждого PR тоже возможны, но требуют создания и удаления Workers/D1, подготовки тестовых данных и секретов. На D1 Free доступно до 10 баз на аккаунт; поэтому для работы вдвоём сначала используем общий QA.
