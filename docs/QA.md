# Civilist: отдельный тестовый стенд

QA — второй экземпляр приложения для проверки изменений перед выпуском. Ветка GitHub хранит версию кода; стенд запускает эту версию по отдельному адресу. Пока используем один общий QA-стенд и развёртываем на него проверяемые ветки по очереди.

## Что уже подготовлено

4 октября 2026 года Дмитрий создал тестовую D1 и проверил её командой `wrangler d1 info`. В момент создания в ней было 0 таблиц.

| Часть | Основной сайт | QA |
|---|---|---|
| Worker | `civilist` | `civilist-qa` |
| База D1 | `civilist-db` | `civilist-db-qa` |
| Database ID | `96ec156d-d73f-4982-83a9-949745d9c555` | `47958c9b-9065-4a00-b609-05415877143f` |
| Окружение Wrangler | основное, `--env=""` | `--env qa` |
| Файл настроек доступа на Mac | `.civilist-secrets.json` | `.civilist-secrets-qa.json` |
| Файл кодов входа на Mac | `.civilist-access.txt` | `.civilist-access-qa.txt` |
| Команда запуска в Cloudflare | `npm run deploy` | `npm run deploy:qa` |

Ожидаемый адрес после запуска QA: https://civilist-qa.cybenkodmitrij92.workers.dev/. Подтверждением запуска служит адрес в успешном выводе Wrangler. Добавление конфигурации в GitHub само по себе не создаёт работающий стенд.

QA использует отдельную привязку `DB`, отдельные случайные коды входа, ключ подписи сессий и редакционный ключ. Проверка перед запуском требует правильные имена Worker и базы и запрещает совпадение ID тестовой базы с любой основной привязкой D1. Эта же проверка выполняется перед загрузкой QA-секретов.

Команды основного сайта явно выбирают верхний уровень конфигурации через `--env=""`, а команды QA — через `--env qa`. Выбор окружения указан и для миграций, и для загрузки Worker и секретов.

В QA загружаем исходные учебные материалы из репозитория. Прогресс и административные правки основного сайта остаются в его базе. Резервная копия основной базы предназначена для восстановления; для первого запуска QA её импортировать не требуется.

## 1. Получить подготовленную ветку

Открой терминал в папке проекта `civilist` и проверь состояние:

```bash
git status --short --branch
```

Если ниже строки ветки есть изменённые или новые файлы, сначала сохрани нужную работу отдельным коммитом или разберись с этими изменениями. После этого:

```bash
git fetch origin
git switch --track origin/chore/qa-environment
npm ci
```

`fetch` получает сведения о новых ветках. `switch` создаёт локальную копию подготовленной ветки и переключает проект на неё. `npm ci` устанавливает версии инструментов из файла зависимостей.

Если локальная ветка уже существует, вместо `--track` используй `git switch chore/qa-environment`, затем `git pull --ff-only`.

## 2. Проверить и собрать

Выполняй команды по очереди; если какая-либо завершится ошибкой, сначала устрани её:

```bash
npm run typecheck
npm test
npm run build
```

Это проверка типов, автоматические проверки авторизации и разделения окружений, затем сборка интерфейса. Эти команды работают на Mac и не развёртывают сайт.

## 3. Создать тестовые коды входа

```bash
npm run access:create:qa
open -a TextEdit .civilist-access-qa.txt
```

Сохрани отдельно QA-код администратора Дмитрия и QA-код ученицы Софьи. Генератор создаёт `.civilist-secrets-qa.json` и `.civilist-access-qa.txt`; повторный запуск отказывается перезаписывать уже существующие файлы. Если они уже созданы, используй сохранённые файлы.

Файлы с кодами и секретами исключены из Git. Коды и содержимое JSON не нужны в переписке. Database ID в конфигурации является идентификатором, а не средством доступа.

## 4. Запустить QA

Уже выполненный вход в Cloudflare используется и здесь. Если Wrangler попросит авторизацию, выполни `npx wrangler login` и подтверди вход в браузере.

```bash
npm run deploy:qa
```

Команда проверит конфигурацию QA, применит миграции только к `civilist-db-qa` и загрузит Worker `civilist-qa` со статическими файлами. При первом запуске до установки секретов приложение отвечает отказом в доступе — это ожидаемо.

Затем:

```bash
npm run secrets:upload:qa
```

Эта команда устанавливает QA-настройки доступа в тестовый Worker. После успешного завершения открой адрес, выданный Wrangler. При первом авторизованном обращении исходные материалы записываются в QA-базу. Основной прогресс не копируется.

В пределах общего бесплатного тарифа отдельный QA не требует включения Workers Paid. Чтение, запись и хранение всех баз расходуют квоты одного аккаунта. Проблема доступности Cloudflare из РФ сохраняется и для QA; используй работающий VPN для текущего этапа.

## 5. Первая проверка QA

1. Войди QA-кодом ученицы и убедись, что открылись материалы и профиль.
2. Пройди одно задание; обнови страницу и проверь сохранение результата.
3. Войди тем же QA-кодом на другом устройстве и проверь общий тестовый прогресс.
4. Выйди и войди QA-кодом администратора; проверь доступность редактирования.
5. На основном сайте проверь прежние коды входа и ранее сохранённый прогресс. Учебные действия в QA должны быть видны только в QA.

Запиши адрес стенда, проверенный commit (`git log -1 --oneline`), шаги, ожидаемый и фактический результат. Это будет первая QA-проверка отдельного окружения.

## 6. Как будем дорабатывать проект

1. Создаём ветку от свежего `master` под конкретное изменение.
2. Разработчик меняет код и открывает pull request. GitHub Actions проверяет типы, тесты, сборку и обе конфигурации без развёртывания.
3. Собираем проверяемую ветку на Mac и выполняем `npm run deploy:qa`.
4. Дмитрий проверяет изменение на QA и описывает найденные ошибки в pull request.
5. После исправлений и успешной проверки включаем изменение в `master`.
6. Выпускаем проверенный `master` на основной сайт. Сейчас это отдельное действие: автоматическое развёртывание ещё не подключено.

Файлы секретов повторно создавать или загружать при обычном обновлении кода не нужно: установленные секреты сохраняются в Worker. Изменение секретов и схемы данных требует отдельной проверки.

Первый QA запускаем с подготовленной ветки до её слияния. После проверки включаем конфигурацию в `master`, чтобы команды QA были доступны и в следующих рабочих ветках. Отдельный адрес для каждого pull request и автоматическую доставку рассмотрим после успешной ручной проверки общего стенда.
