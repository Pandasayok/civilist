# Civilist: первые браузерные автотесты

Автотест повторяет действия тестировщика: открывает страницу, вводит код, нажимает кнопки и сравнивает результат с ожидаемым. Python описывает сценарий, pytest запускает сценарии и показывает результат, Playwright управляет браузером Chromium.

Сайт продолжает работать на React/Vite и Cloudflare Workers. Python нужен только для тестов.

## Где проходят проверки

`npm run test:ui` создаёт временный каталог, случайные локальные коды и свежую локальную D1, применяет миграции и запускает настоящий Worker с собранным интерфейсом. После браузерных проверок Worker останавливается, временная база и коды удаляются. Каждый тест получает новый браузерный контекст: собственные cookies и хранилище. Внутри одного запуска база общая; сценарии используют независимые материалы и сравнивают прирост опыта с начальным значением.

QA и production нужны для ручной проверки развёрнутой версии. Автоматические браузерные сценарии выполняются на временной локальной копии приложения. Их запуск не требует Cloudflare-токена или кодов владельца. Защита в `conftest.py` отклоняет внешний адрес до чтения кодов и старта браузера.

| Сценарий | Что проверяем |
|---|---|
| Неверный код | Показ ошибки, сохранение страницы входа, отсутствие доступа к API |
| Роль ученика | Скрытая кнопка администрирования, отказ при открытии административного раздела и API |
| Учебный тест | Ввод ответов через реальные элементы формы, обратная связь, итог и прирост XP; сохранение после обновления страницы и входа в новом браузерном контексте |
| Настройки и выход | Сохранение имени и цели, восстановление после перезагрузки, закрытие доступа после выхода |
| Черновик администратора | Заполнение формы, сохранение черновика, чтение после перезагрузки; отсутствие материала у ученика |
| Узкий экран | Вход и переход в документы через нижнее меню при ширине 390 px |

Ответы берутся из `content/seed.json` как тестовые данные. Проверяется работа интерфейса и сохранения, а не правильность правового содержания. Порядок вопросов меняется каждый день, поэтому сценарий находит текущий вопрос по видимому названию. Помощник ввода поддерживает одиночный и множественный выбор, соответствие, порядок и письменный ответ; конкретные типы в десяти вопросах зависят от ежедневной подборки.

Узкий экран — эмуляция в Chromium, а не проверка настоящего iPhone, Android или Safari. Карточки, игровые дела, скачивание документов и все варианты отказов сети ещё требуют расширения покрытия.

## Первый запуск на Mac

Команды вводим в папке проекта `~/Projects/civilist`. Перед переключением ветки посмотри `git status --short --branch`: незавершённые изменения сохраняем в своей ветке. Для первого получения ветки этого PR:

```bash
git fetch origin
git switch --track origin/test/playwright-ui
npm ci
```

Если эта ветка уже есть локально, используй `git switch test/playwright-ui` и `git pull --ff-only`. После включения PR в `master` получай код обычным `git switch master` и `git pull --ff-only origin master`.

Проверь Python:

```bash
python3 --version
```

Поддерживается Python 3.10 и новее; в GitHub Actions используем 3.12. Создай отдельное окружение для пакетов проекта:

```bash
python3 -m venv .venv-ui
source .venv-ui/bin/activate
python -m pip install -r requirements-ui.txt
python -m playwright install chromium
```

`venv` — отдельная папка с инструментами этого проекта. Она исключена из Git. Последняя команда один раз скачивает тестовый Chromium; установка всех браузеров не нужна. Дальнейшие тесты используют уже скачанный браузер.

Собери интерфейс и запусти сценарии:

```bash
npm run build
npm run test:ui
```

Ожидаемый результат: `6 passed`. Команда сама запускает тестовый сервер и выключает его после проверки. По умолчанию браузер работает без окна. Если нужна наглядная проверка:

```bash
npm run test:ui -- --headed --slowmo 200
```

Для одного простого сценария:

```bash
npm run test:ui -- --headed --slowmo 300 -k wrong_code
```

Запуск выбирает Python из `.venv-ui`. При необходимости другой интерпретатор можно указать переменной `CIVILIST_TEST_PYTHON`. В CI используется Python, установленный `setup-python`. Адрес приложения задаёт локальный runner; аргумент выбора внешнего сайта не поддерживается.

## Как читать первый тест

Открой `tests/ui/test_study.py`, функцию `test_wrong_code_keeps_the_app_closed`.

1. `page.goto("/")` открывает приложение.
2. `expect(...).to_be_visible()` проверяет, что показан экран входа.
3. `get_by_label("Код доступа").fill(...)` находит поле по подписи и вводит заведомо неверный тестовый код.
4. `get_by_role("button", name="Войти").click()` нажимает кнопку, как пользователь.
5. Следующие `expect` проверяют ошибку и адрес страницы.
6. `api_status(...)` выполняет `fetch` из самой страницы и проверяет ответ API с той же сессией, которую использует интерфейс: без успешного входа ожидаем 401. У вошедшего ученика административный API должен вернуть 403. Такой запрос учитывает правила браузера для защищённых cookies на локальном HTTP.

`page` — фикстура pytest: подготовленная страница браузера для конкретного теста. `login` — наша фикстура, которая входит временным кодом. Она хранится в `conftest.py` и переиспользуется в других сценариях. `expect` ждёт нужного состояния элемента до таймаута; фиксированные паузы `sleep` не нужны.

В PyCharm выбери интерпретатор `.venv-ui/bin/python`. Для просмотра сценария начинай с команды npm: она поднимает весь тестовый сервер и базу. Прямой запуск pytest без runner остановится с объяснением, поскольку для него не подготовлены временные коды и адрес.

## GitHub Actions и ошибки

После открытия PR workflow **Check Civilist** проверяет TypeScript, 21 тест авторизации и команд, сборку, 49 проверок API и затем эти шесть браузерных сценариев. **Deploy Civilist** использует тот же workflow перед загрузкой QA или production. Упавший браузерный тест останавливает выпуск до применения облачных миграций и публикации Worker.

В **Actions → нужный запуск → check → Check browser flows with Python + Playwright** видны имена сценариев и результат. При падении браузерного сценария в Summary появляется артефакт `civilist-ui-failure`: JUnit-отчёт, скриншот и trace с действиями браузера. Он хранится три дня. В артефакт попадают только результаты работы с временными тестовыми аккаунтами; файлы базы, конфигурация и файлы кодов туда не включаются.

На Mac результаты остаются в `test-results/`, исключённой из Git. Для просмотра trace:

```bash
python -m playwright show-trace путь-к-файлу-trace.zip
```

Если pytest сообщает, что исполняемый файл браузера не найден, повтори `python -m playwright install chromium` внутри `.venv-ui`. Для ошибки пакетов используй `python -m pip install -r requirements-ui.txt`. После изменения интерфейса сначала повтори `npm run build`, иначе браузер будет проверять прежнюю сборку.

## Что сделано и чему учиться дальше

Сначала запусти `wrong_code` с окном и найди в файле каждое действие браузера. Затем прочитай сохранение имени, добавь одну осмысленную проверку ожидаемого результата и запусти только этот сценарий. Изменения тестов делаем в отдельной ветке и PR; автопроверки проверят и сами тесты.

Следующие темы: локаторы и доступные имена, фикстуры, проверка состояния после сохранения, работа с разными пользователями, trace при падении. После этого расширяем покрытие карточек, игровых дел и ошибок сохранения.

Источники: [pytest-плагин Playwright](https://playwright.dev/python/docs/test-runners), [Playwright в CI](https://playwright.dev/python/docs/ci), [проверки с ожиданием](https://playwright.dev/python/docs/test-assertions).
